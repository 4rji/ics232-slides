cd networking/foundations
(Basildog starts.) I'll cover the foundation: the two layered models everyone refers to — OSI and TCP/IP — how an Ethernet frame is structured, how data is wrapped and unwrapped as it moves through the layers, and then IP addressing for both IPv4 and IPv6.
cat osi-model.md
The OSI model is a 7-layer reference model. It's conceptual — it describes WHAT each layer does, not how it's implemented. Read bottom to top: Physical moves raw bits, Data Link handles local delivery with MAC addresses, Network handles logical addressing and routing with IP, Transport gives us ports and reliability, and the top three (Session, Presentation, Application) deal with the application itself. A common memory aid is "Please Do Not Throw Sausage Pizza Away."
cat tcpip-model.md
The TCP/IP model is the practical model the Internet is actually built on. It collapses OSI's seven layers into four. The Application layer here combines OSI's top three; Transport is the same; Internet maps to OSI's Network layer; and Network Access combines Data Link and Physical. When engineers talk about real-world stacks, this is usually the model they mean.
cat osi-vs-tcpip.md
This is how the two models line up. The key relationships: OSI's top three layers all map into TCP/IP's single Application layer. Transport maps one-to-one. OSI's Network layer is TCP/IP's Internet layer — that's where IP lives. And OSI's Data Link plus Physical become TCP/IP's Network Access layer. So they describe the same journey, just at different levels of detail.
cat ethernet-frame.md
At Layer 2, data is carried in Ethernet frames. The frame starts with the destination and source MAC addresses — 6 bytes each, the hardware addresses burned into the NIC. The Type/EtherType field says what's inside (0x0800 means an IPv4 packet). The payload holds the actual packet, between 46 and 1500 bytes — that 1500 is the standard MTU. The FCS at the end is a CRC checksum the receiver uses to detect corruption. The preamble and start-frame delimiter are just for synchronization on the wire.
cat encapsulation.md
Encapsulation is how data gets prepared to send. Starting from the application data, each layer adds its own header as the data moves DOWN the stack: Transport adds a TCP header to make a segment, the Network layer adds an IP header to make a packet, and the Data Link layer adds an Ethernet header to make a frame, which finally goes out as bits. On the receiving side it's the exact reverse — decapsulation — each layer strips and reads its own header and passes the rest up. The unit of data at each layer is called a PDU: segment, packet, frame.
cat data-flow.md
Putting it together: data goes DOWN the sender's stack, across the physical medium, and UP the receiver's stack. The important idea is "peer layers." Even though the data physically travels all the way down and back up, each layer behaves as if it's talking directly to the same layer on the other host — the sender's TCP "talks to" the receiver's TCP, the sender's IP "talks to" the receiver's IP, and so on. That logical peer-to-peer view is what the headers make possible.
cd networking/ip-addressing
(Basildog continues.) Now to addressing. MAC addresses get a frame across one link, but to cross networks we need logical addresses — IP addresses. I'll cover IPv4, IPv6, address classes and subnetting, public vs private addressing, and why IPv6 matters.
cat ipv4.md
An IPv4 address is 32 bits, written as four octets in dotted-decimal — each octet is 8 bits, so each number is 0 to 255. Part of the address identifies the network and part identifies the host; the subnet mask decides where that split happens. 32 bits gives about 4.3 billion addresses, which sounded like plenty in the 1980s but we've essentially run out — and that's the whole reason IPv6 exists.
cat ipv6.md
IPv6 is 128 bits — four times the size of IPv4. It's written as eight groups of four hex digits separated by colons. To keep it readable you can drop leading zeros in each group, and you can replace one run of all-zero groups with a double colon. So the long form on top compresses to the short form below. The address space is effectively unlimited — about 3.4 times ten to the 38th — enough to give every device on earth its own public address many times over.
cat subnetting.md
Historically IPv4 was divided into classes A, B, and C based on the first octet, each with a default mask. Class A networks are huge, Class C are small. Today we mostly use CIDR notation instead — the slash number, like /24, just says how many leading bits are the network portion. The subnet mask is what tells a host which bits are network and which are host, and subnetting lets us carve one big network into smaller ones. Quick example: a /24 reserves 24 bits for the network, leaving 8 bits for hosts, which is 254 usable addresses after reserving the network and broadcast addresses.
cat public-vs-private.md
Not every address is meant for the open Internet. RFC 1918 sets aside three private ranges — that 192.168 network on your home router is the famous one. Private addresses are reused by millions of networks and are never routed on the public Internet, which is why they don't collide. Public addresses are globally unique. NAT — Network Address Translation — is the trick on your router that lets many private devices share one public address. NAT is also part of why IPv4 has lasted as long as it has.
cat ipv6-benefits.md
To wrap up my part: IPv6 isn't just "more addresses." Because every device can have a public address, you get true end-to-end connectivity without NAT in the way. The header is simpler and fixed-size, which makes routing faster. Security with IPsec was designed in from the start. Devices can auto-configure their own address with SLAAC, no DHCP server required. And it replaces inefficient broadcast traffic with targeted multicast. That's the foundation — next, Nick takes us into how TCP actually works.
cd transport/tcp
(Nick Swanson starts.) Thanks. I'm covering the Transport layer — specifically TCP, the protocol that makes reliable connections possible. We'll look at how a connection opens, how data is tracked and acknowledged, how flow is controlled, and then compare TCP to its lightweight cousin, UDP.
cat handshake.md
Before TCP sends any data, it sets up a connection with a three-way handshake. The client sends a SYN with an initial sequence number x. The server replies with a SYN-ACK: it acknowledges x and sends its own sequence number y. The client sends a final ACK. Now both sides have agreed on starting sequence numbers and the connection is established. You'll see exactly these three packets in the live tcpdump demo at the end.
cat seq-ack.md
TCP treats your data as a continuous stream of bytes, and it numbers every byte. The sequence number marks where this segment's data starts in that stream. The acknowledgment number is the receiver saying "I have everything up to here, send me this next." In the example, if I send sequence 1000 carrying 100 bytes, the receiver replies with ACK 1100 — meaning "got bytes 1000 through 1099, give me 1100 next." This is how TCP reorders out-of-order packets and notices when something is missing.
cat windowing.md
If TCP waited for an acknowledgment after every single segment, it would be painfully slow. Windowing fixes that. The window is how many bytes the sender is allowed to have outstanding — unacknowledged — at any moment. The receiver advertises its window in every ACK. A bigger window means more data in flight and higher throughput. As ACKs come back, the window "slides" forward and more data can be sent. It's a continuous balancing act between speed and not overwhelming the receiver.
cat flow-control.md
Flow control is the receiver protecting itself. If the sender is fast and the receiver is slow — maybe its buffer is filling up — the receiver simply advertises a smaller window. If its buffer is completely full it can advertise a window of zero, which tells the sender to stop entirely until it gets a window update. One distinction worth making: flow control is about the RECEIVER's capacity. Congestion control, which is related, is about the NETWORK's capacity. Both exist, but they solve different problems.
cat keepalive.md
A TCP connection can sit idle for a long time with no data. How does each side know the other is still there? Keep-alive messages. After a period of silence, one side sends a tiny probe. If it gets a response, great, the connection stays open. If there's no response after several tries, TCP assumes the peer is gone — maybe it crashed or the cable was pulled — and tears the connection down so it isn't holding resources for a dead session. Keep-alive is usually off by default and tuned by the OS.
cat reliability.md
This slide is the summary of why we call TCP "reliable." Sequence numbers put data back in order. Acknowledgments confirm what arrived. If an ACK doesn't come back in time, TCP retransmits the missing data. Checksums catch corruption. Flow and congestion control keep things from being overwhelmed. And the connection is explicitly opened and gracefully closed. Stack all of that together and you get a protocol that guarantees your data arrives complete and in order. Now — what if you don't need all that? That's UDP.
diff tcp udp
(Nick continues.) TCP gives us all those guarantees, but guarantees cost time and overhead. Sometimes speed matters more than perfection. That's where UDP comes in — let's compare them.
cat tcp-vs-udp.md
Side by side: TCP is connection-oriented — it does the handshake — UDP just fires packets with no setup. TCP guarantees delivery and order; UDP makes no promises, a lost packet is simply lost. TCP retransmits; UDP doesn't even notice. And look at the header sizes: TCP's header is 20 bytes minimum and can grow with options, while UDP's is a tiny fixed 8 bytes. That smaller header and lack of bookkeeping is exactly why UDP is faster and lower latency.
cat speed-overhead.md
The way to think about it: TCP spends extra time and bytes — the handshake, the acknowledgments, retransmissions, a bigger header — to buy you a guarantee. UDP skips all of that to be as fast and lean as possible. The decision always comes down to one question: does it matter if a packet is lost? If yes — a file, a web page, an email — use TCP. If a slightly dropped packet is fine and you can't afford to wait — live voice or video — use UDP.
cat use-cases.md
Real examples. TCP powers the things where every byte must arrive: web browsing, email, FTP file transfers, SSH. UDP powers things where being on time beats being perfect: DNS lookups, DHCP, voice over IP, live video, and online gaming. And there are hybrids — DNS uses UDP for normal queries but switches to TCP for large responses, and newer protocols like QUIC build reliability on top of UDP. With that, I'll hand off to Ritz for DHCP, DNS, and how packets are assembled.
cd services/dhcp-dns
(Ritz742 starts.) I'm covering two services that work quietly in the background but are essential: DHCP, which hands devices their IP configuration automatically, and DNS, which turns names into addresses. Then I'll show how IP packets are actually built and taken apart.
cat dhcp-purpose.md
Every device on a network needs an IP address, a subnet mask, a gateway, and DNS servers. Imagine configuring all of that by hand on every phone and laptop — DHCP automates it. When a device joins the network, the DHCP server leases it a complete configuration from a managed pool of addresses, called a scope. It runs over UDP, with the server on port 67 and the client on port 68. The exchange has a memorable name: DORA.
cat dora.md
DORA stands for Discover, Offer, Request, Acknowledge. The client has no IP yet, so it broadcasts a DISCOVER — "is there a DHCP server out there?" Any server replies with an OFFER containing an available IP. The client broadcasts a REQUEST formally asking for that specific offer — broadcast, so any other servers know which offer it took. The server confirms with an ACKNOWLEDGE, and now the client is fully configured. These are the four messages to recognize whenever you inspect a DHCP capture.
cat dhcp-lease.md
A DHCP address isn't permanent — it's a lease with a time limit. About halfway through the lease, the client tries to renew directly with the server. If that fails, at around seven-eighths of the lease it broadcasts a rebind to any server. If the lease fully expires, the client gives up the address and starts DORA over. The whole point of leasing is efficiency: addresses for devices that have left the network eventually return to the pool to be reused.
cat dns-purpose.md
People remember names like example.com; computers route using IP addresses. DNS bridges that gap — it's often called the phonebook of the Internet. It's not one giant server; it's a distributed, hierarchical system spread across the world, which is what makes it fast and resilient. It runs mostly over UDP on port 53, switching to TCP for large responses or zone transfers between servers.
cat dns-resolution.md
Here's how a name gets resolved. Your device asks a resolver — usually your ISP's or something like 8.8.8.8. If the resolver doesn't already know the answer, it walks the hierarchy: it asks a root server who handles .com, the root points it to the .com TLD servers, the TLD points it to example.com's authoritative name server, and that server gives the actual IP. The resolver caches the answer so the next lookup is instant. We'll watch a real query and response in the demo.
cat dns-records.md
DNS stores different record types for different jobs. An A record maps a name to an IPv4 address; AAAA — the "quad-A" — maps to an IPv6 address. A CNAME is an alias pointing one name at another, so www.example.com can point to example.com. An MX record tells mail servers where to deliver email for a domain. There are others — NS for name servers, TXT for things like SPF, PTR for reverse lookups — but A, AAAA, CNAME, and MX are the ones you'll meet most.
cd networking/packets
(Ritz742 continues.) Now down to the packet level — how an IP packet is actually built from application data, what's inside it, and what happens when a packet is too big for the network it has to cross.
cat packet-build.md
This is encapsulation again, but now from the packet's point of view. The application hands its data to the transport layer, which wraps it with a TCP or UDP header to make a segment or datagram. The network layer wraps that with an IP header to make a packet — adding the source and destination IP addresses. Then the link layer wraps it in a frame for transmission. Each layer adds exactly the control information that layer needs.
cat headers-payload.md
If you laid a packet out flat, this is what you'd see: a stack of headers followed by the payload. The Ethernet header has MAC addresses, the IP header has IP addresses, the TCP header has port numbers and flags, and then finally the actual data. A header is just control information; the payload is the cargo. The elegant part is that each layer only looks at its own header and treats everything inside as opaque payload — that separation is what lets the whole stack be modular.
cat fragmentation.md
Sometimes a packet is bigger than a particular link can carry. When that happens with IPv4, the packet is fragmented — split into smaller pieces. The IP header carries the fields needed to put it back together: an identification number, flags, and a fragment offset. Reassembly happens only at the final destination, not at each router. The downside: if even one fragment is lost, the entire original packet has to be discarded and resent. IPv6 changed this so only the sending host can fragment, which keeps routers faster.
cat mtu.md
MTU is the maximum size of payload a single frame can carry on a given link. For standard Ethernet that's 1500 bytes. If a packet exceeds the MTU it gets fragmented — or dropped entirely if the "Don't Fragment" flag is set. Path MTU Discovery is how hosts find the smallest MTU along the entire route so they can size packets to avoid fragmentation. Some high-speed local networks use jumbo frames up to around 9000 bytes for efficiency. With that, I'll hand over to BlongVang for the application protocols.
cd app-layer/protocols
(BlongVang starts.) We've worked our way up the network stack, and now we're at the application layer, the protocols people use every day. I'll cover FTP, HTTP, POP3, and IMAP, including what they do, their default ports, common uses, and the security risks to know.
cat protocols.md
All four protocols use TCP because they require reliable communication. FTP transfers files, HTTP powers the web, and POP3 and IMAP handle email. Remember these default ports: FTP 21, HTTP 80, POP3 110, and IMAP 143. Each also has a secure TLS version.
cat ftp.md
FTP transfers files using two connections: port 21 for commands and a separate connection for data. Passive mode is commonly used because it works better with firewalls. Users log in with a username and password or anonymously on public servers.
cat ftp-commands.md
The main FTP commands are USER, PASS, LIST, RETR, STOR, PASV, and QUIT. FTP is often used for website uploads, backups, and file servers. However, classic FTP sends usernames, passwords, and files in plain text, so secure alternatives like FTPS or SFTP should always be used.
cat http.md
HTTP is the protocol of the web. The client — your browser — sends a request for a resource, and the server sends back a response. Default port 80, or 443 for HTTPS which is just HTTP wrapped in TLS encryption. HTTP is stateless: each request stands alone and the server doesn't inherently remember you between requests. That's why cookies and tokens exist — they add session state on top of an otherwise stateless protocol.
cat http-methods.md
Common HTTP methods include GET, POST, PUT, and DELETE. Servers respond with status codes such as 200 for success, 404 for not found, and 500 for server errors. Since HTTP sends data unencrypted, HTTPS should always be used to protect information.
cat pop3.md
POP3 is an older email protocol that downloads messages to one device and usually removes them from the server. It uses port 110 or port 995 with encryption. Because standard POP3 sends data in plain text, the encrypted version is recommended.
cat imap.md
IMAP stores email on the server and synchronizes messages across all devices. Reading or deleting an email on one device updates every other device. It uses port 143 or port 993 with encryption, making it the standard choice for modern email.
cat pop3-vs-imap.md
POP3 is designed for one device and offline access, while IMAP supports multiple devices by keeping messages on the server. IMAP also synchronizes folders and read status, making it the better option for most users today.
cat protocol-security.md
The biggest issue with the original versions of these protocols is that they send usernames, passwords, and data in plain text. During our demo, you'll see how easy it is to capture FTP credentials. Using TLS through FTPS, HTTPS, POP3S, and IMAPS encrypts traffic and protects data. Next, Havi will demonstrate these protocols live.
